# Topics Covered

## 프로젝트 구조

- **코드**: 재현 가능해야 한다 — 다른 사람이 같은 코드를 실행하면 (무작위성을
  고정했을 때) 같은 결과가 나와야 한다. 데이터 전처리부터 최종 평가까지 전체
  파이프라인이 스크립트/노트북으로 정리돼 있어야 한다.
- **리포트**: 문제 정의 → 방법론 → 실험 결과 → (필수) 수식적 정당화 1개 이상 →
  한계와 향후 개선 방향의 구조를 따른다.
- **포스터**: 발표(W12)에서 쓸 요약본 — 핵심 그림 1~2개(학습 곡선, 결과 예시 등)와
  가장 중요한 결론 3~4개로 압축한다.

## 팀 프로젝트에서 자주 마주치는 실전 문제들

이번 학기 배운 개념들이 실제 프로젝트에서 어떤 모습으로 나타나는지 미리 짚어본다:

- **데이터가 생각보다 지저분하다**: 결측값, 이상치, 클래스 불균형(W03의
  Precision/Recall이 왜 필요한지 다시 체감하게 되는 지점) 등을 먼저 확인해야
  한다.
- **학습이 안 될 때**: 손실이 줄지 않는다면 학습률(W02)이 문제인지, 그래디언트
  소실(W08)이 문제인지, 데이터 자체에 신호가 없는지 순서대로 의심해봐야 한다.
- **검증 없이 모델을 고르지 않는다**: 학습 데이터에 대한 성능만 보고 모델을 고르면
  과적합(W08)된 모델을 최종안으로 선택하는 실수를 하기 쉽다 — 반드시 별도의
  검증/테스트 데이터로 최종 평가한다.

## 수식적 정당화 예시

다음은 "수식적 정당화" 요구사항을 만족하는 예시들이다 (프로젝트 주제에 맞게
변형):

1. 특정 손실함수를 골랐다면, 그 손실함수의 그래디언트가 왜 문제에 적합한 형태를
   갖는지 유도(W02, W03의 패턴 재사용).
2. 정규화 기법(dropout, 가중치 감쇠 등)을 썼다면, 그것이 과적합을 어떻게 줄이는지
   수식 또는 직관적 논증으로 설명(W08).
3. 모델 구조를 선택한 이유를, 파라미터 수/계산 복잡도 공식으로 정량적으로
   비교(W09의 CNN 파라미터 수 계산 패턴 재사용).
4. 강화학습/생성형 프로젝트라면, W05~W10에서 배운 벨만방정식·ELBO·Nash 균형 같은
   개념 중 하나를 실제 구현과 연결지어 설명.

## 평가 기준

- 문제 정의의 명확성
- 방법론의 적절성 (배운 개념을 올바르게 적용했는가)
- 수식적 정당화의 정확성과 깊이
- 결과의 정직한 보고 (잘 안 된 부분을 숨기지 않고, 원인을 분석했는가)
- 코드의 재현 가능성
