### MCTS: 네 단계의 반복

MCTS는 현재 상태에서 시작해, 정해진 횟수만큼 다음 네 단계를 반복해서
"어떤 수가 가장 유망한가"에 대한 통계를 쌓는다:

1. **선택**(Selection): 트리의 루트(현재 상태)에서 시작해, 각 갈림길에서
   "지금까지의 성과"와 "아직 덜 시도해본 정도"를 함께 고려하는 규칙
   (Chapter 2.2의 UCB와 정확히 같은 발상)으로 자식 노드를 골라가며
   아직 다 확장되지 않은 노드까지 내려간다.
2. **확장**(Expansion): 그 노드에 새로운 자식 노드(아직 안 가본 수)를
   하나 추가한다.
3. **시뮬레이션**(Simulation/Rollout): 그 새 노드에서부터 게임이 끝날
   때까지 (간단한 정책으로, 극단적으로는 완전히 무작위로) 끝까지
   플레이해본다 — Chapter 5의 몬테카를로처럼, 실제로 끝까지 해보고
   결과(승/패)를 얻는다.
4. **역전파**(Backpropagation): 그 결과를, 선택 단계에서 지나온 모든
   노드에 통계로 반영한다(방문 횟수 +1, 승률 갱신) — 이 "역전파"는
   ML1 Chapter 9의 역전파와 이름만 같을 뿐 완전히 다른 개념이다:
   신경망의 그래디언트를 전달하는 게 아니라, 트리의 승패 통계를
   전달하는 것이다.

이 네 단계를 수백~수만 번 반복한 뒤, 루트에서 **가장 많이 방문된**
자식(가장 유망하다고 반복적으로 확인된 수)을 실제로 둘 수로 선택한다.
(가장 많이 방문된 것과 승률이 가장 높은 것은 대개 일치하지만
항상 같은 것은 아니다 — 아래 "자주 묻는 질문"에서 다룬다.)

"무작위로 끝까지 해보고(시뮬레이션), 그 결과를 트리의 통계로
적재적재하게 나누어 모은다(선택+역전파)"는 이 아이디어의 계보는
1990년대 오톨로(Othello) 프로그램의 moa* 알고리즘까지 거슬러 올라간다.
2006년 Kocsis와 Szepesvári가 이 가문의 방법들을 **UCT**(Upper
Confidence bound applied to Trees)라는 이름으로 정리하며, Chapter 2.2의
팔레트 아머드 밴딧(bandit) 문제를 트리 탐색에 연결하는 정확한 수식을
줬고, 이 UCT가 바로 오늘 배울 선택 규칙이다. 이후 MCTS는 바둑,
체스, 광물자원 게임 등 "경우의 수가 너무 많아 완전탐색이 불가능한"
문제들의 표준 계획 알고리즘이 되었으며, 2016년 AlphaGo의 핵심
구성요소가 되었다.

네 단계가 **왜** 저 순서로 결합되어야 하는지, 하나의 시뮬레이션을
따라가보자. 루트(돌 5개, 내 차례)에서 시작하면: ① 선택 — 루트에 자식
이 하나도 없으므로 루트에서 즉시 정지한다. ② 확장 — 아직 안 가본
수(예: "2개 가져가기")를 무작위로 하나 골라 자식으로 추가한다.
③ 시뮬레이션 — 그 새 노드(돌 3개, 상대 차례)부터 무작위 플레이로
게임 끝까지 두어 승자를 판정한다. ④ 역전파 — 루트와 그 새 자식,
두 노드 모두에 "방문 1회"를 더하고, 승자가 "그 노드로 **두어
도달한 플레이어**"라면 승 1회도 더한다. 첫 3회 시뮬레이션은
세 갈림의 각각을 한 번씩 열어보는 데 쓰인다(방문 0인 자식은
항상 우선되기 때문) — "모든 수가 최소 한 번은 시도된다"는
보장이 여기에서 온다. 4회차부터 선택 단계의 UCT가 실제로
작용하기 시작한다.

### UCT: 선택 단계의 규칙

선택 단계의 "성과 + 덜 시도해본 정도"는 UCB1의 수식과 **정확히 같은
형태**다. 노드 \\(s\\)에서 자식 \\(a\\)를 고를 때:

\\[ \text{UCT}(s, a) \\;=\\; \frac{Q(s,a)}{N(s,a)} \\;+\\; c\\, \sqrt{\frac{\ln N(s)}{N(s,a)}} \\]

여기서 \\(Q(s,a)\\)는 자식 \\(a\\)의 누적 승(수), \\(N(s,a)\\)는 방문 횟수,
\\(N(s)\\)는 부모 \\(s\\)의 방문 횟수다. 첫 번째 항은 **활용**
("이 수의 승률이 얼마나 높은가"), 두 번째 항은 **탐험**
("이 수를 얼마나 덜 보았는가")이다. 탐험 항의 크기는 대략
\\(1/\sqrt{N(s,a)}\\)로 감소한다 — 한 수가 4번 시도되면 탐험 보너스가
절반으로, 100번이면 1/10로 줄어든다. 그래서 "명백히 낮은 수"는
결국 소수 몇 번의 추가 시도로 방치되고, "경합 중인 수들"은
비례해서 계속 분배된다. 코드로:

```python
import math

def uct_select(node_children, parent_visits, c=1.4):
    # node_children: {move: (wins, visits)}
    # UCB1과 정확히 같은 형태 -- Chapter 2.2를 그대로 게임 트리에 적용한 것
    return max(node_children, key=lambda m: node_children[m][0] / node_children[m][1] +
               c * math.sqrt(math.log(parent_visits) / node_children[m][1]))
```

숫자로 체감해보자. 부모가 16회 방문됐고, 자식 세 개가
`A: 승 7/방문 10`, `B: 승 3/방문 5`, `C: 승 0/방문 1`일 때
(\\(c = 1.4\\)):

- A: \\(7/10 + 1.4\sqrt{\ln 16 / 10} = 0.70 + 0.27 = 1.437\\)
- B: \\(3/5 + 1.4\sqrt{\ln 16 / 5} = 0.60 + 0.59 = 1.643\\)
- C: \\(0/1 + 1.4\sqrt{\ln 16 / 1} = 0.00 + 1.44 \approx 2.331\\)

**승률 0인 C가 선택된다.** "지금까지 한번도 이겨본 적 없다"는
수인데 왜인가? — 아직 1번밖에 시도하지 않았으므로, "진짜 나쁜
수"일 가능성과 "아직 제대로 평가되지 못한 수"일 가능성이
분간되지 않기 때문이다. C를 몇 번 더 보내면, 진짜 나쁘다면
승률이 확인되고 탐험 항이 줄어 자연스럽게 방치되고, 운 좋게
괜찮다면 활용 항이 올라와 본격적으로 승부수가 된다 —
Chapter 2.2의 탐험-활용 트레이드오프가 트리 탐색에서
그대로 작동하는 모습이다. (15.3절의 연습문제 1이 바로 이
계산을 빈칸으로 준 문제다.)

### MCTS 전체 알고리즘

이제 네 단계를 하나의 함수로 조립한다. 게임은 "돌을 1~3개씩
번갈아 가져가고 마지막 돌을 가져가는 쪽이 이기는" 님(Nim) 게임이다.
노드는 **그 노드에서 "이동한 플레이어"(mover)의 관점**의 통계를
담는다는 점에 주목하라 — 역전파가 무엇을 어떻게 더하는지가
전부 여기서 결정된다:

```python
import math
import random

def nim_moves(state):
    """이 상태에서 가능한 수: 남은 돌 수만큼, 1개/2개/3개 가져가기."""
    return list(range(1, min(3, state) + 1))

def nim_step(state, move, player):
    """move개를 가져간다: 남은 돌이 줄고, 상대 차례가 된다."""
    return max(0, state - move), -player

def nim_terminal(state):
    return state == 0

def nim_rollout(state, player, rng):
    """시뮬레이션(롤아웃): 완전히 무작위 정책으로 끝까지. 승자(마지막
    돌을 가져간 플레이어) 반환. 이미 종료된 상태면 막 이동한 쪽이 승자."""
    if nim_terminal(state):
        return -player
    s, p = state, player
    while not nim_terminal(s):
        s, p = nim_step(s, rng.choice(nim_moves(s)), p)
    return -p

class MCTSNode:
    def __init__(self, state, player, parent=None):
        self.state = state        # 상태
        self.player = player      # 이 상태의 차례인 플레이어
        self.parent = parent      # 부모 노드 (역전파를 타고 올라갈 용도)
        self.children = {}        # {move: 자식 노드}
        self.visits = 0           # 방문 횟수
        self.wins = 0.0           # "이 노드로 두어 도달한 플레이어"의 승 수

def mcts_nim(stones, iters, c=1.4, seed=0):
    """돌이 stones개인 님 게임에서 루트 위치의 MCTS. 루트 노드 반환."""
    rng = random.Random(seed)
    root = MCTSNode(stones, player=1, parent=None)
    for _ in range(iters):
        # 1) 선택: "아직 다 확장되지 않은 리프"까지 UCT로 내려간다.
        node = root
        while not nim_terminal(node.state) and len(node.children) == len(nim_moves(node.state)):
            node = max(node.children.values(), key=lambda ch:
                       ch.wins / ch.visits + c * math.sqrt(math.log(node.visits) / ch.visits)
                       if ch.visits else float('inf'))
        # 2) 확장: 안 가본 수 하나를 자식으로 추가. (이미 끝난 상태면 확장 생략)
        if not nim_terminal(node.state):
            unexpanded = [m for m in nim_moves(node.state) if m not in node.children]
            m = rng.choice(unexpanded)
            next_state, next_player = nim_step(node.state, m, node.player)
            node.children[m] = MCTSNode(next_state, next_player, parent=node)
            leaf = node.children[m]
        else:
            leaf = node
        # 3) 시뮬레이션: 리프에서 무작위 정책으로 끝까지, 승자 판정
        winner = nim_rollout(leaf.state, leaf.player, rng)
        # 4) 역전파: 지나온 모든 노드 방문 +1; 승자가 mover면 승 +1
        cur = leaf
        while cur is not None:
            cur.visits += 1
            mover = cur.parent.player if cur.parent is not None else cur.player
            cur.wins += 1.0 if winner == mover else 0.0
            cur = cur.parent
    return root
```

코드의 세 자잘한(그러나 치명적인) 지점을 짚고 지나간다.

**선택의 정지 조건 — "아직 다 확장되지 않은 리프"까지.** `while`
조건이 `len(node.children) == len(nim_moves(node.state))`인
이유는, 자식이 일부만 있는(부분 확장) 노드에서 UCT로 계속
내려가면 안 되기 때문이다. 아직 한 번도 열어보지 않은 자식이
남아 있으면, 우선 그걸 열어야(확장의 "모든 수를 최소 한 번"
보장) 트리의 통계가 공정해진다. 이 조건을 `while node.children:`
으로 잘못 쓰면 모든 방문이 첫 번째로 열린 자식 하나에 집중되는
버그가 나온다 — 아래 "버그 투어"에서 실증한다.

**역전파의 관점 — "mover"에게 승을 더한다.** `mover`는 "이 노드로
**이동한** 플레이어"다. 자식 노드라면 부모의 차례인 플레이어
(`cur.parent.player`)이고, 루트라면 — 이동한 플레이어가 없으므로
(`parent is None`) 현재 차례 플레이어를 대신 쓰되, 루트 자체의
통계는 자식 선택에 쓰이지 않으므로(\\(\ln N(s)\\)에 \\(N(s)\\)만
들어가므로) 무해하다. 이 한 줄이 틀리면 — "차례인 플레이어"에게
승을 더하면 — UCT가 **상대에게 유리한 수를 좋은 수로 착각**하게
된다. 왜 그런지는 역시 버그 투어에서 숫자로 본다.

**터미널 상태의 확장.** 게임이 이미 끝난 노드(돌 0개)에서는
`nim_moves`가 빈 리스트를 돌려주므로, 터미널 검사를 하지 않고
확장을 시도하면 `IndexError`가 난다. `nim_rollout`도 같은 이유로
첫 줄에 터미널 처리가 있다 — "돌을 다 가져간 쪽이 이긴다"는
규칙을 코드로 옮길 때, "누가 마지막에 이동했는가"를
`-player`(차례가 **전달되기 전**의 플레이어)로 판정해야 한다는
점에 주의하라.

### 왜 추정값이 수렴하는가: 트리와 롤아웃의 역할 분담

이제 위 함수를 돌리고, 결과가 **왜** 그런 값이 되는지 이해하자.
먼저 기준선을 잡는다. MCTS 없이, "1개 가져가기"를 둔 뒤 남은
게임(돌 4개, 상대 차례)을 **양쪽 다 무작위**로 끝까지 할 때
나의 승률은 얼마인가? "돌 \\(n\\)개에서 **차례인 쪽**의 무작위 승률"을
\\(P(n)\\)이라고 하면, 규칙 그대로 재귀된다:

\\[ P(1)=1, \quad P(n) = \frac{1}{k(n)} \sum\_{m} \bigl(1 - P(n-m)\bigr) \\]

(\\(k(n)\\)은 가능한 수의 개수, \\(n \le 3\\)이면 \\(k=n\\)). 손으로:
\\(P(1)=1\\), \\(P(2) = (1-P(1) + 1)/2 = 1/2\\),
\\(P(3) = (1-P(2) + 1-P(1) + 1)/3 = 1/2\\),
\\(P(4) = (1-P(3) + 1-P(2) + 1-P(1))/3 = 1/3\\).
그러므로 5개에서 "1개 가져가기"(상대에게 4개를 남기는 수)의
무작위 승률은 \\(1 - P(4) = 2/3 \approx 67\\%\\), "2개/3개
가져가기"는 각각 \\(1/2\\)다 — 순수 무작위 플레이로는 승패를
**약 17%p 차이**로밖에 구분할 수 없다(실제 측정: 0.671 / 0.505 /
0.496). 그런데 MCTS의 추정 승률은 98.7%로, 67%를 훨씬
**뛰어넘는다**. 이 갭이 MCTS의 핵심을 보여준다.

MCTS의 승률 추정치는 "트리가 기억한 것"과 "롤아웃이 표본추출한
것"의 **합성**이다. "1개 가져가기" 자식으로 내려간 뒤, 상대가
돌 4개에서 1개/2개/3개 중 아무 수를 둬도 **나에겐 필승 답이
존재**한다(상대가 \\(m\\)개를 가져가면 내가 \\(4-m\\)개를 가져가면
된다). 트리가 이 "2수짜리 구조"를 노드의 승패 통계로 저장하게
되면, 그 아래에서 나가는 모든 롤아웃은 사실상 "이미 결정된
승부"를 재확인하는 데 불과해, 승률 추정이 100%에 수렴한다 —
"무작위 상대를 상대로 67%"라는 수치가 담지 못 하는
"상대 대응을 무작위가 아니라 **최적 응답으로** 읽는다"는
정보가 트리에 들어간 결과다. 반대로, 트리가 아직 깊숙이
파고들지 못한 깊은 위치에서는 추정치가 여전히 순수 무작위
승률(그 위치의 \\(1-P(\cdot)\\))에 가깝다. 즉 **트리는 "기억할
수 있는 부분"(짧은 범위의 강제 구조)을, 롤아웃은 "기억하기
엔 너무 큰 부분"(나머지 깊은 게임)을 담당**한다 — 이 분업이
MCTS를 "무작위 시뮬레이션"보다, "무작위 시뮬레이션 + 선택적
기억"으로 만드며, 15.1절에서 본 "완전탐색 없이 표본추출만으로
최적 전략을 찾는다"는 주장의 정확한 메커니즘이 이것이다.

이 수렴이 실제로 어떻게 일어나는지, 이기는 수(1개 가져가기)의
방문 점유율과 추정 승률을 시뮬레이션 횟수별로 추적하면(시드 0):

| 시뮬레이션 횟수 | 100 | 200 | 500 | 1000 | 2000 | 5000 | 10000 |
|---|---|---|---|---|---|---|---|
| 1개 수 방문 점유율 | 76% | 86% | 94% | 96% | 98% | 99% | 99.5% |
| 1개 수 추정 승률 | 0.84 | 0.90 | 0.95 | 0.97 | 0.98 | 0.99 | 1.00 |

![MCTS 수렴 곡선 — (a) 이기는 수("1개 가져가기")의 방문 점유율을

"1만 회면 충분한가?" — 이 게임(남은 깊이가 5 이하)에서는 그렇다.

같은 횟수로 같은 정확도는 기대할 수 없으니, AlphaGo는 한 수당
수 초~수 분의 컴퓨트를 배정했다(FAQ 참고).

### 실습 1: 님 게임에서 MCTS로 최적 전략 찾아내기

돌을 1~3개씩 번갈아 가져가고, 마지막 돌을 가져가는 사람이 이기는
간단한 게임(님 게임의 변형)을 생각해보자. 이 게임의 수학적 필승
전략은 잘 알려져 있다 — 상대에게 남기는 돌 수가 **4의 배수**가
되도록 만드는 것이다. 돌이 5개 남았다면 1개를 가져가서 4개를
남겨야 최적이다. MCTS가 이 규칙을 전혀 모른 채로도 이 전략을 스스로
찾아내는지, 선택-확장-시뮬레이션-역전파 4단계를 그대로 구현해서
확인해보자(전체 구현은 이 절 상단의 Colab 노트북 참고, 핵심은 15.1의
UCT 선택과 Chapter 5식 무작위 롤아웃):

```python
root = mcts_nim(stones=5, iters=3000, seed=0)
for move, child in sorted(root.children.items()):
    print(f"  {move}개 가져가기: 승률={child.wins/child.visits:.3f}, 방문={child.visits}/3000")
```

노트북에서 실행 검증한 결과(시드를 0~4로 바꿔가며 5회 반복해도
결과는 일관됐다):

```
  1개 가져가기: 승률=0.987, 방문=2954/3000
  2개 가져가기: 승률=0.269, 방문=26/3000
  3개 가져가기: 승률=0.150, 방문=20/3000
```

MCTS는 "1개를 가져가서 상대에게 4개를 남기는" 수를 3000번 중
2954번(98.5%) 골랐고, 그 수의 승률도 98.7%로 가장 높게 나타났다 —
정확히 수학적 필승 전략과 일치한다. 게임의 규칙 자체(4의 배수
전략)를 MCTS는 전혀 몰랐는데도, 오직 "시뮬레이션을 많이 해보고 이긴
비율이 높은 수를 고른다"는 것만으로 이 최적 전략을 스스로 찾아낸
것이다. 나머지 두 수(2개, 3개 가져가기)의 방문 횟수가 완전히
0으로 떨어지지 않고 20~26회씩 남아있는 것도 흥미로운 지점이다 —
UCB 항 덕분에 "덜 시도해본 수"에는 계속 소량의 탐험 예산이
배정되기 때문이다(Chapter 2.2에서 배운 탐험-활용 트레이드오프가
게임 트리 탐색에서도 그대로 작동하는 것을 보여준다). 그리고 이
"0으로 안 떨어진다"는 점은 실전에서도 중요하다 — **MCTS의 출력은
"확률적 추천"이다.** 탐색 예산이 부족하면 아직 충분히 확인되지
않은 수에도 방문이 남기 때문에, 중요한 국면(끝물)에서는 추가
시뮬레이션으로 확신을 높이는 게 표준적이다.

### 실습 2: 더 큰 국면(14개)과 탐색 상수 \\(c\\)의 효과

4의 배수 규칙은 국면이 커져도 동일해야 한다 — 돌 14개라면
\\(14 - 2 = 12\\)를 남겨야 하므로 **"2개 가져가기"가 최적**이다.
5000회 시뮬레이션(seed 0) 결과:

```
  1개 가져가기: 승률=0.488, 방문=498/5000
  2개 가져가기: 승률=0.830, 방문=4198/5000
  3개 가져가기: 승률=0.441, 방문=304/5000
```

방문 점유율은 14개 국면에서도 필승 수("2개")에 84%가 집중됐다 —
4의 배수 규칙을 국면 크기와 무관하게 찾은 셈이다. 그런데 추정
승률이 5개 국면의 98.7%에 비해 **83.0%로 낮다**. 이 차이, 즉
"국면이 클수록 같은 시뮬레이션 횟수에서 수렴이 느리다"는 것이
중요한 교훈이다. 위에서 본 "트리 + 롤아웃 합성" 관점으로 보면,
"2개"를 둔 뒤 남은 게임이 돌 12개로 **길다** — 트리가
"기억할 수 있는" 짧은 범위의 강제 구조(14개에서 2개를 둔 직후
1~2수)가 전체 게임에 차지하는 비중이 작아지고, 나머지는 더 길고
더 노이즈가 큰 무작위 롤아웃으로 채워지기 때문이다. 실제로
이어서 5만 회까지 돌리면 97.8%까지 올라간다 — 천장이 낮은 게
아니라 **도달에 시간이 걸리는** 것이다.

여기에 한 겹 더 있다. "무작위 상대를 상대로 한 참 승률"이라는
기준선 자체가 국면이 클수록 내려간다. 5개에서 이기는 수("1개")의
무작위 상대 참 승률은 \\(2/3 \\approx 67\\%\\)였지만, 14개에서
이기는 수("2개")는 — "2개"를 두고 남은 12개를 무작위로
끝냈을 때 나의 승률, 즉 \\(1-P(12) \\approx 0.504\\),
**50.4%**다(돌 12개에서 차례인 쪽의 무작위 승률
\\(P(12)\\approx0.496\\) — 거의 동전 던지기). MCTS 추정치
(83%)는 이 무작위 참승률(50%)을 훨씬 뛰어넘지만, 완전탐색
기준의 상한(100%)에는 아직 못 미친 어딘가다. 실전 바둑에서는 이
두 극단("무작위 참승률"과 "최선 상한")이 거의 0과 1로 벌어져,
무작위 롤아웃 하나당 담기는 신호가 극도로 희박해진다 — AlphaGo가
신경망 롤아웃으로 갈 이유(아래 절)의 극한 버전이다.

탐색 상수 \\(c\\)를 바꿔도(2000회, seed 0) 이기는 수는 항상 1위지만,
탐험 예산의 **분배**가 \\(c\\)에 따라 달라진다:

| \\(c\\) | 1개 수: 승률/방문 | 2개 수: 승률/방문 | 3개 수: 승률/방문 |
|---|---|---|---|
| 0.8 | 0.992 / 1983 | 0.300 / 10 | 0.143 / 7 |
| 1.4 | 0.982 / 1956 | 0.280 / 25 | 0.158 / 19 |
| 2.5 | 0.954 / 1879 | 0.275 / 69 | 0.154 / 52 |

\\(c\\)를 키우면 "덜 시도해본 수"에 배정되는 예산이 커져, 확실히
나쁜 수에도 69~70회나 방문이 배분된다. **\\(c\\)는 "확률적으로 보이는 이득"과 "미래 정보 가치"를 어떻게
트레이드오프하느냐의 다이얼**이다 —
Chapter 2.2의 UCB에서 \\(c\\)를 데이터 스케일에 맞춰 튜닝했던 것과
같은 논리다(실제 게임에서는 \\(c \approx 1.4\\) 근방을 기본값으로
두고, 게임의 확률적 정도에 따라 검증으로 조절한다).

### 실습 3: 틱택토의 첫 수 (15.1절과 연결)

15.1절에서는 틱택토를 **완전탐색**(549,946개 국면)으로 풀어
"최선이면 무승부"라는 **정확한** 답을 구했다. 같은 게임을 이번엔
MCTS로 풀어보자 — 빈판에서 5000회 시뮬레이션(\\(c=1.4\\), 시드
0/1/2) 후, 첫 수 후보 9개의 통계를 비교하면:

```
시드 0 (5000회):  가운데(4) — 승률 0.740, 방문 1667 (33%)
                  네 귀퉁이 — 승률 0.62~0.68, 방문 431~670 (각 9~13%)
                  나머지(가운데 끼인 변) — 승률 0.54~0.63, 방문 183~380
```

세 시드 모두 **가운데**가 방문 점유율(29~41%)과 승률(0.72~0.76)
둘 다에서 1위였다. 완전탐색과 MCTS의 답을 **같은 눈으로** 읽어야
한다는 점을 짚자: 완전탐색의 "무승부"는 **양쪽이 모두 최선일 때**의
결과였고, MCTS의 승률은 **상대가 무작위 플레이를 할 때**의
실전 승률이다. 틱택토엔 "필승" 수가 없으므로, MCTS의 순위는
"바보 상대를 상대로 얼마나 자주 이기고(=상대가 실수할수록 이득이
크고), 얼마나 적게 지는가"를 반영한 것 — 그 관점에서도
"가운데 → 귀퉁이 → 변"은 정석적 순서와 일치한다. 두 방법의
출력을 서로 다른 질문의 답(정확한 가치 vs 표본 기반 추천)으로
읽는 연습, 이것이 계획 알고리즘을 쓸 때의 기본 태도다.

### 버그 투어: 실제로 다 발붙여 본 네 가지 실수

MCTS 구현이 "에러 없이 돌면서" 결과가 이상할 때, 그 원인은 대부분
아래 네 가지 중 하나다. 모두 위에서 검증 실행으로 증상까지
재현한 것들이다(노트북의 마지막 섹션에서 직접 바꿀 수 있다).

1. **선택 루프가 부분 확장 노드에서 멈추지 않는다.** 정지 조건을
   `while node.children:`으로 쓰면, 루트의 자식 중 **첫 번째로
   열린 하나**에 모든 방문이 집중된다(재현: 3000회 중 한 자식
   3000, 나머지 두 자식 0). UCT는 사실상 작동하지 않고, 어떤 수가
   살아남을지는 "우연히 먼저 확장된 수"가 정하는 셈이다. 증상
   특이점: "결과가 너무 한쪽으로 쏠려 있고, 시드만 바꿔도 쏠리는
   수가 바뀐다."
2. **역전파 관점 반전.** 승을 "차례인 플레이어"(`cur.player`)에게
   더하면, UCT는 **상대에게 유리한 수**를 "좋은 수"로 착각한다 —
   재현 결과, 방문이 1072/1037/891로 거의 균등(1/3씩)이 되어
   이기는 수를 전혀 구별 못 한다. 승률 수치 자체도 0.01~0.03처럼
   의미 없는 값이 된다. 증상 특이점: "방문 분포가 고르게
   퍼져있다"는 건 보통 탐험이 과대하다는 뜻인데, 여기선
   **신호가 완전히 사라진** 경우다.
3. **승을 아예 안 더하고 방문만 더한다.** \\(Q\\)가 항상 0이면
   UCT의 활용 항이 사라져 탐험 항만으로 동작하게 되고, 방문은
   정확히 1/3씩(재현: 1000/1000/1000) 균등해진다 —
   "UCB가 균등 분배한다"는 Chapter 2.2의 성질이 그대로
   재현되는 셈이다.
4. **터미널 상태에서 확장을 시도한다.** `IndexError`로
   크래시한다(재현: 돌 0개 노드에서 `nim_moves`가 빈 리스트).
   에러 메시지는 명확하지만, "왜 리프에서 확장을 했지?"를
   묻게 되는 유형이다.

네 버그의 공통점은, 마지막 하나를 빼면 **에러가 안 나고 "결과가
조금 이상하다"로만 나타난다는** 점이다 — 계획 알고리즘 디버깅에서
가장 사악한 형태. 그래서 이 절의 실습이 "답을 수학적으로
알 수 있는 게임"(님) 위에서 한다는 데 의도가 있다: "방문
분포가 알려진 정답에 집중하는가?" 자체가 **테스트**가
된다. 답을 알 수 없는 게임(바둑)에서 구현을 디버깅할 때는,
이름을 바꿔가며 위 네 가지 변형을 직접 만들어가며 "증상과
결과의 대응"을 체득하는 게 표준적인 방법이다.

### AlphaGo/AlphaZero: MCTS와 신경망의 결합

순수 MCTS는 시뮬레이션 단계에서 무작위로(또는 아주 단순한 규칙으로)
게임을 끝까지 진행한다 — 님 게임처럼 승패가 몇 수 안에 명확해지는
게임에서는 무작위 롤아웃도 충분히 정확한 신호를 준다. 하지만
바둑처럼 한 수의 영향이 아주 나중에야 드러나는 게임에서는, 무작위로
끝까지 두는 롤아웃 하나하나가 사실상 노이즈에 가까워서 부정확할 수
있다. AlphaGo와 그 후속작 AlphaZero의 핵심 개선은, 이 무작위 롤아웃을
**신경망**으로 대체한 것이다: 신경망 하나가 "이 상태에서 각 수가
얼마나 유망한가"(정책, Chapter 10.1의 \\(\pi\_\theta\\)와 같은
역할)를, 다른 하나(또는 같은 신경망의 다른 출력 헤드)가 "이 상태가
최종적으로 얼마나 유리한가"(가치, Chapter 3.3의 \\(V(s)\\)와 같은
역할)를 추정한다. MCTS는 이 신경망들의 추정치를 길잡이 삼아 탐색을
훨씬 더 효율적으로 좁혀나가고, 그렇게 MCTS로 찾아낸 더 정확한 수를
다시 신경망 학습의 정답(지도학습 목표)으로 사용한다 —
**탐색(MCTS)과 학습(신경망)이 서로를 개선하는 루프**다.

이 결합에서 선택 규칙도 UCT에서 **PUCT**로 발전한다:

\\[ \text{PUCT}(s,a) \\;=\\; \frac{Q(s,a)}{N(s)+N(s,a)} \\;+\\; c\_{\text{puct}}\\,
P\_{\theta}(s,a)\\, \frac{\sqrt{N(s)}}{1+N(s,a)} \\]

차이는 탐험 항이다. UCT의 탐험 항 \\(c\sqrt{\ln N(s)/N(s,a)}\\)는
"시도 안 된 수"에 **균등하게** 보너스를 주지만, PUCT는
**정책 신경망의 사전확률** \\(P\_\theta(s,a)\\)로 **가중**한다 —
"신경망의 직관"이 탐색의 방향을 정하고, MCTS가 그 직관을
검증·수정하는 통계로 되돌려주는 식이다. 활용 항도 \\(Q/(N+N(a))\\)
로 부드럽게 정교해졌다. 학습 루프를 한 바퀴 더 구체화하면:
(1) 자기 자신과의 대국(self-play)으로 경험을 만들고, (2) MCTS로
각 국면을 탐색한 **방문 분포**로 정책망을 지도학습시키고, (3)
게임의 **최종 승패**로 가치망을 지도학습시키며, (4) 더 나은
망으로 다시 self-play를 돌린다. AlphaZero(2017)는 이 루프만으로,
게임 규칙만 알려주고(데이터 없이) 바둑·체스·상체를 전부
마스터했다 — "탐색과 학습이 서로를 개선한다"는 이 절의 핵심
문장이, 신경망이 아니라 **알고리즘 루프 자체**로 성립했음을
보여준 것이다.

왜 바둑에 이런 무기가 필요했는지를 숫자로 보자. 19×19 바둑판에서
단 **81수만** 두어도 가능한 수순은 \\(19^{81} \approx 10^{104}\\)
개다. 한 판(양쪽 합쳐 280~300수, 한쪽은 약 80수)은 그 트리의
약 80개 리프만을 탐색한다. **100억 판**(\\(10^{10}\\))을
끝없이 두어도 도달하는 국면은 약 \\(8 \times 10^{11} \approx
10^{12}\\)개 — 전체 국면 수 \\(10^{170}\\)의 \\(10^{-158}\\)
부분이다. 완전탐색이라는 "정직한 방법"이 성립하지 않는
규모에서, "유망한 가지만 표본추출로 파고든다"는 MCTS의
원칙(15.1절 틱택토 실습의 격차의 극한)이 사실상 **유일한**
길이었다 — 그리고 그 표본추출의 방향을 신경망이 가중해준
PUCT + self-play 루프가 이세돌 승부를 만들어냈다.

### 자주 하는 실수: 롤아웃 정책과 시뮬레이션 횟수를 혼동하기

MCTS를 처음 구현할 때 흔히 겪는 두 가지 실수가 있다. 첫째, **롤아웃
정책을 너무 정교하게 만들려는 것**이다 — "무작위 롤아웃은 부정확하니
정교한 규칙을 넣자"는 생각으로 롤아웃 자체에 복잡한 로직을 넣으면,
시뮬레이션 한 번의 계산 비용이 커져서 같은 시간 안에 훨씬 적은
횟수만 시뮬레이션하게 된다 — 위 님 게임 실습처럼 오히려 "단순하지만
많이" 도는 쪽이 나을 때가 많다. AlphaZero가 신경망으로 롤아웃을
대체한 것도 "더 똑똑하게"가 아니라 "한 번의 평가로 승패 시뮬레이션
수백 번을 대체할 만큼 신뢰도 높은 신호를 준다"는 효율성 계산이
깔려 있다. 둘째, **UCT 탐험 상수 \\(c\\)를 문제와 무관하게 고정하는
것**이다 — 위 실습의 `c=1.4`는 님 게임에는 잘 맞았지만, 승/패 대신
연속적인 점수를 다루는 문제에서는 값의 스케일이 다르므로 \\(c\\)를
다시 튜닝해야 한다(Chapter 2.2에서 UCB의 \\(c\\)를 데이터 스케일에
맞춰 조정해야 했던 것과 같은 이유다).

### 자주 묻는 질문

**Q. 위(15.2절) 님 게임 예제와 15.1절(틱택토) 예제는 왜 다른 방법을
쓰나요?** 틱택토는 상태 수(549,946개)가 완전탐색이 가능할 만큼
작아서 minimax로 "100% 정확한" 답을 구했다. 님 게임도 사실 상태
수가 작아서 완전탐색이 가능하지만, 일부러 MCTS로 풀어서 "완전탐색
없이 표본추출만으로도 최적 전략을 찾아낼 수 있다"는 것을 보여주기
위한 예제다 — 실전에서 MCTS를 쓰는 이유는 바둑처럼 완전탐색이
아예 불가능한 문제이기 때문이다.

**Q. MCTS는 지도학습이나 강화학습 알고리즘인가요?** 엄밀히는 둘 다
아니다 — **계획(planning)** 알고리즘이다. Chapter 4의 가치반복처럼
모델(규칙)이 있다는 전제하에 "지금 무엇을 할지"를 계산하는 방법이지,
Chapter 9~11처럼 파라미터를 경사하강으로 갱신해 정책을 학습하는
알고리즘이 아니다. AlphaZero가 강력한 이유는 정확히 이 계획
알고리즘(MCTS)과 학습 알고리즘(신경망 지도학습)을 루프로 엮었기
때문이다.

**Q. 최종 수를 고를 때 "가장 많이 방문된" 자식과 "승률이 가장
높은" 자식 중 어느 쪽을 고르나요?** 표준은 **방문 최대**(most
visits)다. 방문이 적을 때 승률 추정치는 노이져스한데(20번 중 3번
이긴 수와 100번 중 30번 이긴 수는 승률이 같아도 신뢰도가
다르다), 방문 횟수는 UCT가 "여기를 더 봐야겠다"고 판단한
**양** 자체라서 견고하다. 시뮬레이션 횟수가 충분히 많으면 두
지표는 대개 같은 수를 가리키며(위 실습에서 그랬듯), 예산이
끝났을 때 승률 격차가 확실히 큰 예외 상황에서만 승률 최대를
쓰는 변형도 있다.

**Q. MCTS가 보여주는 "승률 98.7%"는, 실제로 무작위 상대와
맞대결했을 때의 승률(67%)과 같은 의미인가요?** 아니다 — 이
구분의 이해가 "트리와 롤아웃의 역할 분담" 절의 핵심이다.
98.7%는 **트리가 "상대 대응에 대한 내 필승 응답"을 통계에
저장한 뒤**의 합성 추정치로, 순수 무작위 승률(2/3)을
뛰어넘는다. 시뮬레이션을 늘리면 님처럼 끝이 짧은 게임에서는
100%("최선-최선" 기준의 참 승률)에 수렴하고, 바둑처럼 긴
게임에서는 "무작위 참승률"과 "최선 상한" 사이의 어딘가에
수렴한다 — 그 위치가 바로 신경망 롤아웃이 개입하는 곳이다.

**Q. 시뮬레이션은 몇 번이면 충분한가요?** 닫힌 형태의 공식이
있지 않다 — (1) 수렴 곡선이 평탄해진다(이기는 수의 방문 점유율이
고정값에 다가서는가), (2) **수의 순위**가 시뮬레이션 추가에
대해 변하지 않는가로 실측해 판단한다. 예산 배분의 경험칙은
"중요한 수(결정적 국면)에, 쓸 수 있는 만큼" — AlphaGo는 한 수당
CPU 수 초~수 분을 썼고, 남은 깊이가 짧은 끝물에서는 수렴이
훨씬 빨라 같은 횟수로 더 정확한 추정이 나온다.
