15.1 모델기반 RL 개관: Dyna-Q 재조명과 “공짜 모델”

Dyna-Q 복습: 학습된 모델로 가상 경험 만들기

Chapter 7.3의 Dyna-Q는 세 가지를 동시에 했다: (1) 실제 환경과 상호작용해 경험을 쌓고, (2) 그 경험으로 간단한 모델 \(\hat{P}(s’|s,a)\), \(\hat{R}(s,a)\)을 학습하고, (3) 그 모델로 가상의 추가 경험을 만들어 Q값을 더 많이 갱신했다. 모델기반 강화학습(Model-Based RL)은 이 아이디어를 일반화한 이름이다 — 환경의 모델(전이확률과 보상함수, 또는 그 근사)을 학습하거나 이미 알고 있다면, 그 모델을 이용해 “실제로 행동해보지 않고도” 여러 수를 미리 시뮬레이션해볼 수 있다는 것이다. Dyna-Q가 이 시뮬레이션을 값 갱신에 썼다면, 이번 장의 MCTS는 이걸 지금 당장 어떤 행동을 할지 결정하는 데 직접 쓴다는 점이 다르다.

모델이 “공짜“인 경우: 체스와 바둑

체스나 바둑 같은 게임에는 특별한 사정이 있다 — 규칙이 완벽하게 알려져 있다. “이 수를 두면 판이 정확히 이렇게 바뀐다“는 전이확률 \(P(s’|s,a)\)를 Dyna-Q처럼 데이터로부터 배울 필요가 전혀 없이, 이미 정확히 알고 있는 것이다(Chapter 4의 모델 기반 방법을 쓸 수 있는 이상적인 조건이다). 문제는 상태 수가 너무 많다는 것이다 — 바둑판의 가능한 국면 수는 약 \(2 \times 10^{170}\)으로 추정되는데, Chapter 4.3의 가치반복처럼 모든 상태를 한 번씩 순회하며 계산하는 방식은 근본적으로 불가능하다. 그래서 “지금 당장 놓인 상황 근처만” 깊이 파고드는 탐색이 필요해진다 — 이게 바로 15.2절 MCTS가 풀려는 문제다.

실습: 완전탐색이 가능한 경우와 불가능한 경우

“모델을 알고 있다“고 해서 항상 완전탐색(minimax)을 쓸 수 있는 건 아니다 — 상태 수가 관건이다. 틀만 같고 상태 수가 훨씬 작은 틱택토(3×3 빙고)에서 완전탐색이 실제로 가능한지 확인해보자:

WIN_LINES = [(0,1,2),(3,4,5),(6,7,8),(0,3,6),(1,4,7),(2,5,8),(0,4,8),(2,4,6)]
nodes_visited = 0

def winner(board):
    for a, b, c in WIN_LINES:
        if board[a] != 0 and board[a] == board[b] == board[c]:
            return board[a]
    return 0

def minimax(board, player):
    global nodes_visited
    nodes_visited += 1
    w = winner(board)
    if w != 0:
        return w
    if all(x != 0 for x in board):
        return 0  # 무승부
    scores = []
    for i in range(9):
        if board[i] == 0:
            board[i] = player
            scores.append(minimax(board, -player))
            board[i] = 0
    return max(scores) if player == 1 else min(scores)

result = minimax([0]*9, player=1)
print("완전탐색 결과 (1=선공승, 0=무승부, -1=후공승):", result)
print("탐색한 전체 국면 수:", nodes_visited)

스크래치패드에서 실행 검증한 결과:

완전탐색 결과 (1=선공승, 0=무승부, -1=후공승): 0
탐색한 전체 국면 수: 549946

두 선수가 모두 최선을 다하면 틱택토는 항상 무승부로 끝난다 — 그리고 이 결론을 얻는 데 필요한 국면 수는 549,946개로, 평범한 노트북에서 1초도 안 걸려 전부 훑을 수 있다. 반면 바둑은 국면 수가 이보다 \(10^{165}\)배 이상 많다 — 완전탐색이라는 “정직한” 방법 자체가 아예 성립하지 않는 규모다. 이 격차가 바로 15.2절에서 다룰 MCTS가 필요한 이유다: 전체 트리를 다 보는 대신, 유망해 보이는 가지만 표본추출(sampling)로 골라서 깊이 파고든다.

자주 하는 실수: “모델이 있으니 학습이 필요 없다“는 착각

모델기반 RL을 처음 배울 때 흔한 오해가 있다 — “환경의 규칙을 완벽히 안다면, Chapter 4의 가치반복 같은 계획(planning) 알고리즘만으로 바로 최적 정책을 계산할 수 있으니 신경망 학습이 아예 필요 없다“는 생각이다. 위 실습에서 봤듯, 이건 상태 수가 작을 때만 맞는 말이다. 바둑처럼 상태 수가 천문학적인 문제에서는 “모델을 안다“는 것과 “그 모델로 최적 행동을 실제로 계산할 수 있다“는 것이 전혀 다른 얘기다 — 그래서 AlphaGo/AlphaZero(15.2절)는 여전히 신경망을 학습시킨다. 반대로 Dyna-Q(Chapter 7.3)처럼 모델이 데이터로부터 학습된 것일 때는, 그 모델 자체의 오차가 Q값에 누적되는 문제도 있다 — 초기에 몇 안 되는 경험으로 학습한 부정확한 모델을 가지고 가상 경험을 너무 많이 만들면, 그 부정확함이 그대로 Q값에 스며들어 오히려 학습을 방해할 수 있다. “모델기반“이라고 해서 공짜로 정확한 답을 주는 게 아니라, 모델의 정확도(또는 완전성)와 상태 공간의 크기 둘 다가 계획의 실현 가능성을 결정한다는 점을 기억해두자.

자주 묻는 질문

Q. Chapter 4의 가치반복도 “모델기반“인데, 왜 이 장에서 다시 “모델기반 RL“이라는 용어를 쓰나요? 맞다, 가치반복도 모델기반이다. 차이는 스케일과 쓰임새다 — Chapter 4는 상태가 적은 문제에서 정책 전체를 미리 다 계산해 두는 데 썼다면, 이번 장(Dyna-Q, MCTS)은 상태가 너무 많아 정책 전체를 계산할 수 없을 때 “지금 이 상태에서 무엇을 할지“만 필요한 순간에 계산하는 데 초점을 맞춘다.

Q. 그러면 모델기반 RL이 모델없는(model-free) RL(Chapter 5~11의 대부분)보다 항상 좋은가요? 아니다. 모델기반 RL은 정확한 모델(또는 잘 학습된 모델)이 있을 때 데이터 효율이 훨씬 좋지만, 모델 자체를 학습하는 비용과 오차 누적 위험이 있다. 로봇 팔처럼 물리 법칙이 복잡한 환경에서는 정확한 모델을 만들기 어려워, Chapter 9~13처럼 모델 없이 직접 정책/가치를 배우는 쪽이 더 실용적인 경우가 많다.
